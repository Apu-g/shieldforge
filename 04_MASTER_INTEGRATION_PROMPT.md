# Master Integration Prompt

Run this **once all four people have a working, individually-tested module** (every checkbox in their section of `03_PART_PROMPTS.md` is checked). Paste this whole prompt into your coding AI with repo access to all four folders.

---

```
You are integrating four independently-built modules of a hackathon security
platform called ShieldForge into one working, deployable system. Each module
has already passed its own standalone acceptance tests (see 03_PART_PROMPTS.md
for what "done" meant for each). Your job is NOT to rewrite modules — it is to
wire the real connections where mocks currently exist, following the contracts
in 02_INTEGRATION_README.md exactly.

REPO LAYOUT YOU ARE WORKING WITH
proxy/        — Part 1, Next.js, currently mocks the ML call and the Supabase write
ml-service/   — Part 2, FastAPI, already deployed and standalone-tested
dashboard/    — Part 3, Next.js + Supabase, owns supabase/schema.sql
victim-app/   — Part 4a, standalone, already deployed
llm-agent/    — Part 4b, currently tested with a mock finding JSON

DO THIS IN ORDER — do not skip ahead or parallelize these steps, each depends
on the last being verified:

STEP 1 — Shared environment
- Collect every value in .env.example from 01_ARCHITECTURE.md §6 from the
  person who generated it (Supabase project from Part 3, ML service URL from
  Part 2, LLM keys from whoever registered them).
- Populate .env.local in proxy/, dashboard/, and llm-agent/ with the real values.
- Confirm dashboard/supabase/schema.sql has actually been run against the
  shared Supabase project and Realtime is enabled on events, findings, incidents.

STEP 2 — Proxy ↔ ML service (real connection)
- In proxy/, flip USE_REAL_ML to true and point ML_SERVICE_URL at the real
  deployed ml-service/ URL.
- Send one known-malicious test request through the proxy
  (`<script>` in a query param) and confirm:
  a) the proxy still returns a 403 (rule-based path still works), AND
  b) a request that only the ML model would catch (something subtler, ask
     Part 2 for an example from their test set) also gets classified
     correctly end to end.
- If ml-service is unreachable, confirm the proxy fails open to rule-based
  blocking only — do not let the whole proxy go down because the ML call failed.

STEP 3 — Proxy ↔ Supabase (real connection)
- In proxy/, flip WRITE_TO_SUPABASE to true.
- Send a test request through the proxy and confirm a real row appears in
  the events table, and — if confidence crosses the policy threshold — real
  rows appear in findings and incidents.
- Confirm no cookie values, tokens, or passwords ever appear in any written
  row — grep the actual DB rows for this, don't just trust the code.

STEP 4 — Origin registration (real victim app)
- In the dashboard, use the real origin-onboarding UI to register the real
  deployed victim-app URL.
- Confirm the proxy, using the config Part 3's dashboard wrote (not the
  hardcoded mock), correctly forwards to the real victim app.

STEP 5 — LLM agent ↔ real findings table
- Point llm-agent/'s polling loop at the real Supabase project instead of
  the mock JSON.
- Confirm that a finding generated by a real attack in Step 2/3 gets a real
  ai_summary written back and appears on the live dashboard without manual
  intervention.

STEP 6 — Full end-to-end demo rehearsal
Run the exact flow from 01_ARCHITECTURE.md §1, for real, twice:
1. Deploy/confirm victim app is live.
2. Register it as an origin via the dashboard.
3. Fire the XSS/cookie-theft payload at the PROXIED url (not the raw
   victim-app url — that's the whole point).
4. Confirm, in order: event logged → finding created → ML classification
   attached → ai_summary appears → policy-driven action taken (block/alert
   per the configured mode) → audit_log row written.
5. Click "Verify fix" and confirm the finding flips to fixed_verified.
6. Trigger the phishing simulation and confirm a risk score updates and a
   lesson_assigned event appears on the training tab.

STEP 7 — Resilience check (judges will ask about this)
- Stop the ml-service entirely. Repeat the attack. Confirm the proxy still
  blocks via rules and the dashboard still shows SOMETHING (even without
  ML-derived fields) — this proves the fail-open design claim in the pitch.
- Restart it, confirm it resumes contributing ML fields on the next attack.

STEP 8 — Final report
Produce a short INTEGRATION_RESULTS.md listing:
- Each of the 8 steps above and pass/fail
- Any contract deviation you had to make and why (there should ideally be
  none — flag loudly if you had to change a shape from
  02_INTEGRATION_README.md, since that means someone's module needs a
  follow-up patch)
- The final list of live URLs (proxy, dashboard, ml-service, victim-app) for
  the demo

Do not refactor module internals you don't own. If a module's code doesn't
match its documented contract, the fix is to adjust the connecting glue code
first and only touch the module itself if there's truly no other way — note
it in INTEGRATION_RESULTS.md either way so the owner knows.
```

## After integration: the 60-second pitch checklist

- [ ] Can you do the full demo flow live, without slides, in under 2 minutes?
- [ ] Do you have the "detection time" chart on screen as visible proof of the 50% claim?
- [ ] Do you say out loud: "this uses Vercel's cold starts as the demo data plane; production would move the proxy to a dedicated process" — judges respect stated limits more than hidden ones?
- [ ] Do you show the fail-open behavior (ML down, rules still protect) as a deliberate feature, not an accident?
- [ ] Do you mention the CERT-In 6-hour export as the India-specific differentiator?
- [ ] Is all attack traffic demonstrated against your own deployed victim-app only?
